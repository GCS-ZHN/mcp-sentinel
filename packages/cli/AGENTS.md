# mcp-sentinel-cli — development notes

These notes apply to `packages/cli` (publishes `@gcszhn/mcp-sentinel-cli`).
They supplement the repository-root `AGENTS.md`, which governs git flow,
lockstep versioning, CI, and the project-wide tool/testing standards.

## This is a harness-agnostic MCP CLI, not a Codex plugin

- The package ships `cli.js` (bin `mcp-sentinel`) exposing the four
  `mcp_sentinel_*` tools as a stdio MCP server. It is usable in **any** harness
  (Codex, OpenCode, DeepSeek Harness, …) by registering it as an ordinary MCP
  server.
- It is **not** a `.codex-plugin/` bundle, has no marketplace entry, and is not
  installed via `codex plugin add`. Codex plugins are not true SDK-integrated
  in-process plugins and custom marketplaces caused strange runtime issues, so
  the plugin form is deliberately abandoned.
- Do not re-introduce `plugin/.codex-plugin`, `.mcp.json`, or `skills/` inside
  this package.

## CLI surface

```bash
mcp-sentinel mcp --harness <codex|opencode|custom|none> [--mcp-config <file>]
```

- `--harness codex` — discover MCP servers via `codex mcp list --json`.
- `--harness opencode` — discover via `opencode debug config` (JSON `mcp` object).
- `--harness custom` — load a JSON file via `--mcp-config` (`servers` /
  `mcpServers` / bare map of raw entries).
- `--harness none` — empty config.

The sentinel skips entries the harness disabled (`enabled: false`, or Codex's
`disabled_reason`) and its own entry. Self-detection matches the entry's launch
`command` against the sentinel's own `process.argv` (`selfProcessCommand()` +
`sameCommand()` in `src/config.ts`) — never the server name — so a self entry
registered under any name is still skipped.

## Config field names (do not guess — read the source)

Each source maps its harness's own field names into the core `McpConfig`:

| Concept        | Codex (`mcp list --json`)                                    | OpenCode / Custom (`environment`, `headers`) | Core `McpConfig`    |
| -------------- | ------------------------------------------------------------ | -------------------------------------------- | ------------------- |
| local command  | `command` + `args`                                           | `command` (string[])                         | `command: string[]` |
| local cwd      | `cwd`                                                        | `cwd`                                        | `cwd`               |
| local env      | `env` + `env_vars`                                           | `environment`                                | `env`               |
| remote url     | `url`                                                        | `url`                                        | `url`               |
| remote headers | `http_headers` + `env_http_headers` + `bearer_token_env_var` | `headers`                                    | `headers`           |
| transport type | `stdio` / `streamable_http`                                  | `local` / `remote`                           | `local` / `remote`  |

Codex remote is `type: "streamable_http"` and stores headers under
`http_headers` (not `headers`); OpenCode stores the local env map under
`environment` (not `env`). Reading the wrong name would silently yield
`undefined`, so every read is guarded before casting.

The custom `--mcp-config` file follows OpenCode's entry field names
(`environment`, `headers`) and is documented by a JSON Schema at
`schema/mcp-config.schema.json` (shipped in the npm tarball via the package
`files` list). Keep the schema in sync with `CustomMcpConfigSource.load()`.

## No notification channel

The CLI deliberately sets `setNotifier(null)`: as a generic MCP server it has no
harness message channel (no OpenCode `promptAsync`, no Codex hook). Agents
collect results with `mcp_sentinel_attach` / `mcp_sentinel_status` /
`mcp_sentinel_read`. Do not re-add a spool/hook mechanism here.

## Build artifacts are not committed

- `cli.js` is generated by `bun run build` (`bun build src/cli.ts --outfile
cli.js --target bun`) and is gitignored, along with `dist/`.
- CI runs `bun run build` before `bun test` and `npm publish`, so the npm
  tarball (whose `files` whitelist includes `cli.js`) always carries a fresh
  bundle.

## One-click install (Codex)

```bash
scripts/install-codex-mcp.sh
```

Builds the package and registers `[mcp_servers.mcp-sentinel]` in
`~/.codex/config.toml` as `mcp-sentinel mcp --harness codex`. Start a new thread
afterwards. Other harnesses: register `mcp-sentinel mcp --harness <harness>`
(or `--mcp-config`) as an MCP server in that harness's config.

## Conventions

- `args` and `until` are **native JSON values** in MCP arguments (not JSON
  strings, as in the OpenCode/DeepSeek harness plugins); `src/mcp-server.ts`
  passes them straight through to the core's `handlePoll`.
- The `codex` binary is resolved from `CODEX_BIN`/`CODEX_CLI_PATH` env, then
  PATH, then common install locations; the `opencode` binary from PATH.

## Testing

- Unit tests under `tests/*.test.ts` cover the harness config discovery
  (codex/opencode/custom parsing, self-skip) and a stdio integration smoke test
  (`mcp-server.test.ts`, which boots the built `cli.js mcp --harness custom`
  and runs a full poll against a real stdio MCP server).
- E2E cases live in `tests/e2e-cases.json`; they drive each harness's agent
  against the CLI-registered `mcp_sentinel_*` tools (runner: root AGENTS.md).
  The codex cases require the isolated trusted workdir
  (`/private/tmp/mcp-sentinel-e2e`), a capable model
  (`-m deepseek/deepseek-v4-pro`, since flash cannot reliably discover Codex's
  deferred MCP tools), and `-s danger-full-access` (the default sandbox aborts
  stdio MCP calls).
- **opencode / custom harness cases** run the CLI inside OpenCode (not Codex):
  first create the isolated workdirs with `scripts/setup-cli-e2e-workdirs.sh`,
  which registers `mock-ci` + `mcp-sentinel mcp --harness opencode` (opencode)
  or `mcp-sentinel mcp --harness custom --mcp-config mcp.json` (custom). The
  cases use `opencode run --pure --auto --dir <workdir> -m deepseek/deepseek-v4-pro`:
  `--pure` disables the global OpenCode plugin (avoiding a `mcp_sentinel_*` tool
  name collision), and the `deepseek` provider is required — the `opencode`
  provider's `deepseek-v4-pro` does not reliably follow the poll→attach
  pattern and loops on `mcp_sentinel_poll`.
- **Agent tool discipline.** Each prompt begins with: only use the visible
  `mcp_sentinel_*` tools; do not read local files, do not run shell commands, do
  not inspect configuration.
